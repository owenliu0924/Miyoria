# V5 的玩:卡片、生圖、回收、派對遊戲

> 2026-11-14 規劃,沒有實作。底子是 owner 的 [image-cards.md](image-cards.md)(生圖抽卡企劃)和 [cards.md](cards.md)(每日卡的立繪),加上這次唯讀查詢 `data/miyoria.db` 的帳本和行為紀錄。它是 [v5-architecture.md](v5-architecture.md) §9 的細節。標「草案」的數字都還沒定;§8 是 owner 2026-11-14 的決定和還沒定的事。

## 0. 結論

1. **兩種卡都要花魚幣**:每日卡一張 30,生圖卡一抽 150(草案)。
2. **生圖卡整包暫緩到模型選定,但現在就設計完**。和模型無關的部分(資料、抽卡、底片庫、檢查的管線、面板)可以先用現有的 workflow 在旗標後面做好,選定模型後只換 workflow、重新校準、重新審主題。
3. **生圖走 ComfyUI 的 API**,就是現有的 `imagegen`。ComfyUI 跑在哪一台由 hostd 決定,不一定是這張 12 GB 的卡。
4. **回收**:六天裡發出約 6,400、收回約 3,200,收回的一半以上是餵食;十幾種花費幾乎沒人用。做法是刪掉沒人用的,加上會重複發生、規模跟著餘額走的去處:深海交易所(模擬公司的股票)、每週拍賣、每週樂透、點歌優先券、水族箱。
5. **派對遊戲**六天裡一次都沒開過。留猜歌和海龜湯,讓人能自己開;問答和兩種接龍刪掉。

## 3. 生圖卡

玩法照 [image-cards.md](image-cards.md),這一節只寫「要蓋什麼」和它接進 V5 的方式。

### 3.1 三種東西

| 東西 | 是什麼 | 主要欄位 |
|---|---|---|
| **主題** | 一個 prompt 模板,不是一張圖 | 卡池(常駐 / 某一週的限定)、稀有度、場景 / 服裝 / 動作 / 光線的範圍、反向提示、workflow 代號、檢查門檻、庫存目標、狀態(草稿 / 樣本待審 / 上架 / 下架) |
| **底片** | 一張生好、檢查過、還沒發出去的圖 | 主題、seed 和參數、各項檢查分數、圖(產物庫裡的一個私有產物)、狀態(庫存 / 已發 / 淘汰) |
| **卡** | 發給某個人的一張 | 流水號、主人、底片、她寫的卡面、稀有度、取得時間、是不是封面、是不是覺醒版 |

另外每人每個卡池一筆保底計數,每人每個主題一格圖鑑。

### 3.2 抽一次

1. 扣魚幣(一抽 150、十連 1,350,一天最多 20 抽;庫存低時上限自動調低)。
2. 抽稀有度(N 70 / R 22 / SR 7 / SSR 1),套保底(30 抽必出 SR 以上;限定池 80 抽必出本期 SR 主題,計數跨週延續)。
3. 在那個稀有度裡抽一個主題。
4. 從那個主題的庫存拿一張底片,綁到這張卡,從庫存移除。一張只發一次。
5. 她看圖寫卡面(幾秒)。這段時間畫面上是底片慢慢顯影。
6. 庫存是空的,或抽到 SSR「和你」:這一抽變成「未沖洗的底片」,先公布稀有度和主題,圖好了私訊通知;24 小時內生不出來就退錢。

### 3.3 底片庫

- 每個主題維持庫存量(草案 N 30、R 15、SR 8),低於門檻就排批次工作補。
- 批次工作只在 GPU 有空時跑:經 hostd 的 VRAM 仲裁,她在唱歌或開台時讓位(現有的 `imagegen` 已經會在唱歌時讓出)。
- 每張進庫前過 §3.4 的檢查,沒過就重生,同一格最多重試 3 次。淘汰率記下來,面板看得到每個主題的數字。

### 3.4 檢查和審核

| 檢查 | 抓什麼 | 做法 |
|---|---|---|
| 像不像她 | 臉跑掉、髮色不對 | 和她的參考圖算圖像相似度,低於門檻淘汰。門檻用每個主題的樣本校準 |
| 壞圖 | 多手指、崩臉、糊 | 臉和手的偵測加美感分數 |
| 不該有的內容 | 暴露、血腥 | NSFW 分類器;主題模板本身先過現有的審查和主人規則 |
| 她自己看 | 圖和主題不合 | 她寫卡面時可以回「這張不像我」,就不發,換一張 |

- **owner 審的是主題模板**:上架前看一組樣本(12 張)。之後面板每天隨機抽幾張底片給 owner 看。
- **SSR 和「和你」**:頭一個月每張都先經 owner 看過才沖洗。
- 卡片頁標明「圖由 AI 生成」,有「這張有問題」的檢舉:先隱藏、退錢、進 owner 的待辦。

### 3.5 抽完之後

- **圖鑑**:每個主題一格,抽到就亮。同主題有好幾張時自己挑一張當封面。集滿一個系列給稱號和卡框。
- **覺醒**:同主題 3 張,拿自己挑的那張當參考,用更高品質重繪;另外兩張消失。草案再收 100 魚幣。
- **分解**:不要的卡變成鱗片;鱗片換「指定主題一抽」(選主題,不選圖)。
- **她的參與**:每張卡的卡面是她看圖寫的;SSR 多一句她的語音;抽到 SR 以上和覺醒她會記得;可以拿卡給她看,一天一次。
- **全服相簿**:只放本人同意公開的,不排名。
- **贈送**:一般卡可以送、不能賣;SSR「和你」不能送。草案:送卡收 20 魚幣手續費,一天最多送 3 張,收的人要有基本的羈絆(防小號)。

### 3.6 SSR「和你」

場景只用公開頻道裡的事(聊過的話題、一起玩過的遊戲),不用私訊,也不用她對你的記憶內容;卡上不出現你的臉。一定現場生,排最高優先,但她唱歌時仍然等。

### 3.7 ComfyUI 和顯卡

- 生圖經 ComfyUI 的 API,也就是現有的 `packages/workspace/imagegen`(落地保存的工作佇列、唱歌時讓出顯卡、可以掛自訂 workflow)。**不另外接別家的服務**。
- ComfyUI 是 hostd 管的一個服務,提供 `imagegen` 這個能力,顯卡策略是 `on_demand`。它跑在哪一台是部署的事:原企劃估 Krea 2 Turbo fp8 要 16 GB 起,這張卡是 12 GB,所以十二月選模型時要一起決定「在這台用量化的模型」還是「在另一台電腦跑 ComfyUI」。兩種對 Core 來說是同一個 API。
- 主題只記 workflow 的代號,不記模型。換模型的工作是:新的 workflow 檔、重新校準相似度門檻、每個主題重審一組樣本。底片庫裡舊模型的圖可以發完為止。
- 她的 LoRA:owner 要找網路上那一份並確認授權。原企劃的提醒還在:作者不允許的話,整個企劃要改成委託繪師。

### 3.8 接進 V5

- 表和邏輯在 `cards` 外掛(主題、底片、卡、保底、圖鑑、檢舉)。
- 圖放產物庫(v5-architecture §11.2):底片是私有的,發卡時變成本人可見;進全服相簿才變成有連結就能看。
- 抽到、覺醒、被檢舉都是事件,進她的收件匣。
- 面板:主題(樣本、核可、上下架)、庫存和淘汰率、每日抽查、檢舉、機率表(改動留紀錄)。公開頁有機率表。

## 4. 回收

### 4.1 原則

1. **去處要有下文**:花了錢,自己看得到、她記得、或別人看得到。
2. **會重複發生**:每天或每週都有理由花,不是買一次就沒了。
3. **規模跟著餘額走**:錢多的人自然花得多(拍賣、買賣股票、手續費按比例)。
4. **花錢買不到羈絆**,也不拿感情催人花錢。這兩條是現有的規則。
5. **每週看數字**:目標是回收量至少是發放量的八成。面板已經有經濟健康表。

### 4.4 深海交易所

完整設計在 [exchange.md](exchange.md)。重點:

- **八家假公司**,代號像股票:DPSK(DipSick AI,她的老家)、CLSD(ClosedAI)、GOGL(Goggle)、NVDY(Envydia)、RICE(白飯食品)、WHLE(鯨落唱片)、CUBE(方塊礦業)、NAPS(打盹床業)。owner 2026-11-14:名單照這樣。
- 價格由程式模擬,一天 12 盤,單日漲跌幅 ±10%。新聞的種類和大小由程式抽,她只寫字。幾家公司會被真的事推一點(她的模型 API 塞車時 DPSK 會跌),一天最多 ±3%。
- **事件照真的股市**:週財報、除息、股東會紀念品、併購傳聞、現金增資、升降息、黑天鵝、熔斷、注意股 → 處置股 → 下市、新股抽籤。owner 2026-11-14:下市要開。
- **不印錢**:買股票的錢進金庫,賣的錢從金庫出,所有玩家合起來拿不走比放進去更多的錢。價格跑在資金前面時,大盤會被往下拉。
- **回收**:買賣各 1.5% 手續費,賣出再收 3% 交易稅,全部燒掉。
- 她是財經主播:每天行情圖、每週預估和財報講評;她看不到隱藏的數字,也不下場。
- **交易量表**(取代贊助榜):這一週誰買賣的金額最多。排的是交易量,不是賺賠,也不是身家。
- 上線前先離線模擬,再做兩週不能下單的紙上交易。

### 4.5 拍賣、優先券、樂透

- **每週拍賣**(owner 同意):一週一件,在一個討論串裡公開出價 24 小時,最後 5 分鐘有人出價就延長。得標的錢燒掉,沒得標的全數退回。拍的東西(例):這一週她怎麼叫你(她可以拒絕不雅的)、直播結尾感謝名單的第一位、替水族箱的一條魚取名、一個只此一件的卡框、提名一家新公司上市。
- **點歌優先券**(owner:不要競標,單純的優先券):固定價(草案 40)。用了之後你點的歌排到沒用券的人前面,同樣用券的照先後。一人一天最多兩張。取代現在沒人用的點歌券和獻詞。
- **每週樂透**(owner 同意):一張 10 魚幣,每人每週最多 20 張。獎金是售出金額的七成,三成燒掉。她每週抽一個人。

### 4.6 水族箱

取代房間集資(零筆)。直播畫面和網頁上有一個共用的水族箱:

- 買一條魚或一個擺設(草案 50 到 300),上面掛你的名字。
- 魚每週要飼料(草案 10);沒人餵就「游回深海」。這是持續的回收。
- 她看得到水族箱,會聊誰的魚。它也接上她是鯨魚娘的設定。
- 伺服器一起養到某個數量,解鎖一個新的佈景(取代沒人用的伺服器目標)。

**魚怎麼呈現**(owner 要先看到再決定):

- 魚是程式畫的,不用生圖:十種左右的輪廓 × 配色 × 花紋 × 大小,由購買時的種子決定,每條都不一樣。生圖開放後可以加少數「特別的魚」。
- 直播畫面:底部一條水帶(overlay 已經有畫布),魚游過時偶爾浮出主人的名字。
- 網頁:一整頁的水族箱,滑到魚上顯示名字、哪天買的、被餵了幾次。
- 她的鯨魚剪影偶爾游過;她心情低的時候水色暗一點。
- 動工之前先做一張靜態的示意圖給 owner 看。

工比較大(overlay 和網頁各一個元件),排在交易所之後。

## 6. V5 另外提的三項

這三項不在 owner 的企劃裡,是 V5 加的。owner 2026-11-14:三項都要。

### 6.1 里程碑卡

- **是什麼**:羈絆升到新的分級時(例如朋友 → 好朋友),她給你一張綁定的卡。不能買、不能抽、不能送。
- **卡上有什麼**:當下算的立繪(表情對應新的分級)、日期、她從一段共同記憶寫的一個場面。高分級本來就要一段共同記憶當門檻(v5-architecture §8.3),卡上寫的就是那一段。
- **為什麼要**:升級現在是無聲的,數字變了沒人知道。有了它,升級是一個看得見的時刻;圖鑑裡會多一排「你和她的經過」。
- **隱私**:場面只用你本來就看得到的內容(你們之間的對話),卡預設只有本人看得到。
- **工**:小。用的是每日卡的算圖和卡面。

### 6.2 頻道裡的掉落

- **是什麼**:頻道熱鬧的時候(草案:十分鐘內三個人以上、共二十則以上),她偶爾丟出一張卡,第一個按按鈕的人拿到。
- **不取代付費的每日卡**:掉落的卡帶一個只有掉落才有的限定部件。每人一天最多拿一張,每個頻道一天最多兩三次,要在那個頻道的設定裡打開。
- **為什麼要**:給「人在現場」一個理由,也是幾個人一起的事(誰搶到了會被講)。
- **風險**:會變成搶按鈕;有人用程式自動按。對策是隨機延遲出現、同一個人連續搶到會被跳過。它也是一個不收錢的卡片來源,所以要有上限。
- **工**:小到中。

### 6.3 願望單

- **是什麼**:你標記最多三個想要的部件(生圖卡開放後也可以標主題)。抽到時她會講(「你要的單片眼鏡」)。
- **不改機率**。機率表對每個人都一樣。想指定的話,生圖卡有鱗片可以換指定主題。
- **為什麼要**:她因此知道你喜歡什麼,會記得;抽到時多一句屬於你的話。
- **可以加的變化**(不建議):花魚幣「許願」讓接下來幾張的機率提高。它是一個回收口,但會讓機率表變複雜。
- **工**:很小。

- **每日卡**:`POST /api/member/card` 和 `/me card` 都走 `CardService.issueDaily`:一張 30 魚幣,第一張也要錢,一天 5 張(她的當地日)。先看今天還能不能發、錢夠不夠,才請她寫字,所以被拒的卡不花模型呼叫;她寫的字(一句話、印章、欄位、名字、稱呼)和舊卡一樣寫法,付了錢才寫,寫不出來就退錢。錢包是經濟提供的 `CardWalletKey`(帳本原因 `card_daily`,退回 `card_refund`,以卡號為冪等鍵);陌生人和被封鎖的人收到和陌生人一樣的回答。卡框和閃卡照舊;「重抽」「指定立繪」拿掉(一次性的購買,不退)。**閃卡和卡一起付**(2026-11-17 修):以前是 api 自己用 `<key>:foil` 買閃卡,閃卡退回之後用同一個 key 重送,經濟把那筆已退回的購買當成「重複」回答,卡就免費閃了。現在閃卡是 `CardService.issueDaily` 的一部分:錢包多了 `foilPrice` 和 `foil(付款人, 卡號)`,經濟照一般加購(價格 `card_foil`、每天 `card_foils_per_day`)扣,冪等鍵是卡號,和卡本身那筆一樣;先扣卡、再扣閃卡,閃卡被拒(超過今天的次數 429、錢不夠 402)就把卡那筆退回。退款以卡號找兩筆,卡退成 `card_refund`、閃卡退成經濟自己的 `refund`(和 `Economy.refund` 同一個鍵,兩邊不會都退)。已經退回的扣款再被問到時一律拒絕,不會當成付過。報價一次看卡加閃卡的錢,只夠付一樣的人在扣任何錢之前就被拒;不賣閃卡時回 400「現在不賣閃卡」(以前是 503「錢包現在不能用」)。`/me card` 回報的 `charged` 是這次真的扣的(重送拿到舊卡是 0),不再是照價目表算。
- **舊卡和舊收藏**:舊的會員卡(`member_cards`)原樣留著,照樣驗得到、列在新卡後面、算進張數。舊收藏(`economy_docs` 的 `item`)在模組啟動時複製到 `cards_legacy`(以舊文件 id 為鍵,重複跑不會重複),圖鑑裡是封閉的「舊收藏」系列;選擇複製而不是原地讀,是因為舊目錄和文件表都屬於經濟、之後會拿掉,而圖鑑是這個外掛的。舊的抽收藏整個刪了(程式、工具、指令、設定、面板按鈕)。
- **圖**:`card-face` 畫卡,立繪是用她的 Live2D 模型照抽到的東西現場算的(步驟 3,cards.md §6):`CardPortraitKey` 由 `cards` 模組在 `[modules.cards] portrait = "live2d"`(預設)而且這台電腦算得出來時提供(`live2d.ts`,透過 `tools/card-studio` 的無頭 Edge)。對照表 `portrait-looks.ts` 每個部件、每個表情一列(用模型自己的表情檔、手勢動作的最後一格和參數;背景是程式畫的 SVG;空手、無配件是模型預設),測試保證目錄的 35 個部件和 11 個表情都有一列、沒有多的。種子給姿勢一點偏移,同一張卡同一張圖;圖依規格的雜湊存在 `data/cards/portraits/`,發卡時就先算。算不出來(沒設 `portrait_model`、card-studio 沒建置、沒有 Live2D 的檔案或瀏覽器、逾時、失敗)就回 `null`,用 10 張固定圖裡最接近表情那張(`portrait.ts`:落淚→害羞臉紅、圈圈眼→瞇眼笑、大牙→微笑、黑臉→冷淡,其餘同名),日誌只寫一行。抽到的部件也用文字印在卡上和卡片頁(卡號移進那一條)。卡變成 PNG 時只用專案帶的 Noto Sans TC,不靠系統字型。**同一張卡同一張圖**:三個地方拿到的圖來自同一個函式(`packages/api/src/card-art.ts` 的 `cardArt`):有 `CardPortraitKey` 而且卡有抽卡快照(`CardService.card(編號)` 有紀錄,每種卡都有)就用現場算的圖,否則用 `card.pose` 的固定立繪。舊的會員卡沒有抽卡快照,永遠是它原來那張固定立繪;算圖器沒有、回 `null` 或丟錯,也退回固定立繪(日誌一行)。連結預覽(`/og/card/<編號>.png`)和 `/me card` 用整張卡的圖(`cardPng`:照卡的資料版本快取、一次畫一張,`/me card` 把它附在卡片最上面,是一個只有本人看得到的圖片附件,畫不出來就只有文字);面板的會員頁和卡片頁用只有立繪的 `GET /api/public/card-art/<編號>.png`(`ogRoutes` 裡,公開側開著才有)。這條路由只給公開檢查頁本來就看得到的卡(沒有、格式不對、已作廢或已刪的都是同一個 404,每個來源受 `admitCardCheck` 限速),不會比 `/og/card` 多給任何東西。現場算的圖是快照、永遠不變,所以 `public, max-age=86400, immutable`;退回的固定立繪以後可能被現場算的取代,所以只快取 5 分鐘。面板拿不到(已作廢的舊卡)就照舊用 `/card-<pose>.local.webp`。注意:現場算的圖是不透明的(背景畫好了),閃卡的彩虹遮罩原本用固定立繪的透明背景當遮罩、閃在她以外的地方,換成現場算的圖後遮罩就是整塊立繪,彩虹只剩立繪以外(框、字的區域);樣式沒改。限制:圖還沒進產物庫(`artifact_id` 空著)、「換一雙鞋」要全身入鏡所以人很小;其餘見 cards.md §6.2。
- **API**:`cards` 群組有我的卡、一張卡(只有本人看得到保底、願望、價格)、圖鑑(系列、稱號、舊收藏)、保底、願望單讀寫、公開的機率表;`cardsAdmin` 給面板看一個人的卡。Discord 不加新指令:`/me card` 的 `action` 多了 圖鑑、機率、保底、願望單(`wish:` 最多三個部件名稱,`清空` 清掉)。

- **扣了錢卻沒寫成的卡**(2026-11-17 修):Core 停在扣款和寫卡之間、之後也沒有人用同一個 key 重送,錢以前不會自己退。現在 `cards` 模組啟動時和之後每 5 分鐘(`CardService.settlePending`)看一次 `cards_pending`:超過 2 分鐘的(還在跑的不搶),卡號已經有卡就只刪那一列,否則經錢包把那個卡號下扣的(卡和閃卡)退回再刪。每一列在那個人的順序裡處理,這個程序裡正在發的卡先做完。錢包還沒起來(經濟有自己的啟動順序)、找不到那個人的帳號、退款失敗,那一列留到下一輪。每處理一列寫一行日誌(人的 id、卡號、退了多少),沒有任何人寫的字。退款因此改成以卡號找扣款(不是收據),停在拿到收據之前的也退得到。「忘記我」和合併不再刪這些列:忘記時留著等它退款(錢的紀錄本來就留),合併時交給留下的人(對方也有同一個 key 的就換一個沒人會問的 key,只等退款);判斷「有沒有寫成」看卡號,不看 key。上線前的 `cards_pending` 列(舊程式的閃卡是另外以 `<key>:foil` 扣的)只會退卡那一筆,閃卡要手動看。
- **共同的規則**(里程碑卡、紀念卡、掉落的卡):不用錢、不算進每天 5 張、照公開機率抽但**不用也不動保底**(設計沒寫保底;不用錢的卡動到保底,就是繞過保底的路),部件照樣進圖鑑、可以完成系列。一人一個場合一張,靠 `issue_key` 的唯一索引(`milestone:<分級的下限>`、`keepsake`、`drop:<掉落 id>`),重啟、重送都不會多發。合併兩個人時兩個人都有的同一個 key,被併的那張卡留著、拿掉 key。
- **里程碑卡**(§6.1、P4):heart 在羈絆進入一個從沒到過的分級時(`tier_floor` 往上,在交易提交後)通知聽的人(`HeartStore.onTierEntered`;heart 不認得 play,是 `cards` 模組去聽)。一級一張,認識以上 15 級最多 15 張,小階不給,掉下去再升回來不給;一次跳好幾級就每級一張;搬移和合併不算升級。她的字經 `CardFacesKey`(api 提供,和每日卡同一套寫法和檢查,多告訴她是里程碑卡、到了哪一級,知心以上加上那一級錨點的共同記憶,當成卡上的場面),api 沒開時只有名字。`cards` 模組沒在跑的時候升的級不補發,也不回頭補給已經在高分級的人(他們是紀念卡)。
- **紀念卡**(P5):heart 的搬移留下 `heart_person.legacy.migrated_at` 的人,或 `db import-links` 帶過來、`persons.legacy` 不是空的人,一人一張,第一次打開自己的卡時發(會員頁的 `GET /api/member/card`、卡片列表、圖鑑,`/me card` 的任何 action);`/me card` 那一次只給看紀念卡、不發新卡、不扣錢。卡上是事實不是她寫的字(打開卡片時不等模型):第一次見面的日子、V4 的分級、舊卡張數(知道才印)。不私訊,也不告訴她。被封鎖的人拿不到。一人只有一張(2026-11-17 修):以前「忘記我」刪了卡、`persons.legacy` 還在,從 V4 匯入的人忘記之後再打開卡片會再拿到一張。現在給過紀念卡記在 `cards_keepsake`(只有人的 id 和時間,和卡在同一個交易寫),忘記時卡刪掉、這一列留著,合併時歸留下的人;有這一列但卡不在就不再發。它屬於「人」這個資料類別,和讓人有資格的 `persons.legacy` 一起:清掉關係(卡)兩個都留,清掉人兩個都走。migration 5 建表,並替已經有紀念卡的人補上這一列(時間是那張卡的)。
- **頻道裡的掉落**(§6.2,`drops.ts`,`[modules.cards] drops` 預設關):只在 `drop_channels` 列的頻道(每個頻道自己的開關,用設定、不加指令)。熱鬧照設計的草案(十分鐘內三個人、二十句;她自己、機器人和卡片訊息不算),一個窗口擲一次 `drop_chance`;設計沒定的數字都取保守的、放在設定:機率 0.25、一個頻道一天 2 次(設計說兩三次)、同頻道隔 120 分鐘、隨機延遲 30–180 秒(設計的「隨機延遲出現」)、10 分鐘沒人撿就飄走、一人一天 1 張(設計)。次數記在 `cards_drop`(migration 3),重啟不會重算。卡是中性通知加一個按鈕,按鈕是 `/me card` 的元件路由 `cards:drop`(沒有新指令)。第一個按的人拿到(一個 UPDATE 決定,搶的人同時按也只有一個),先佔住才請她寫字,所以晚到的人不花模型呼叫;沒寫成就放回去給別人。撿到的卡帶一個只有掉落才有的部件(目前只有「頻道裡的煙火」,SR,所以掉落的卡至少是 SR);同一個頻道上一張是你撿的,這張你撿不到(設計的「同一個人連續搶到會被跳過」)。卡只有撿的人看得到(ephemeral 的 follow-up),頻道那則改成「某某撿走了這張卡」;她也會聽到誰撿走了。她不認識或不說的人撿不了。
- **部件目錄**(2026-11-17 加):`GET /api/member/cards/catalogue`(會員,和圖鑑同一個限速)給整個目錄:每個部件的 id、名字、欄位、稀有度、系列和系列的名字、`drop_only`、`blank`、`enabled`,以及 `wishable`(能不能放進願望單,和願望單的檢查用同一個函式 `isWishable`:不是空白、沒停用;只有掉落才有的部件可以,§6.3 說許願不改機率,抽到時她提一句),再加上全部系列(id、名字、稱號)。面板不用再從機率表猜目錄。機率表的每個部件多了 `series_name`。

- **清掉關係時扣了錢還沒寫成的卡**(§11.1,2026-11-17 修):以前 `cards_pending` 屬於「關係」,owner 清掉關係時一起刪,那時剛好扣了錢還沒寫成的卡就沒人退。owner 的決定是「清除前先結清」;資料類別的清除只是一組 SQL,前面不能跑程式(`cards` 模組也不在清除時會停的模組裡),所以做法是讓這張表不屬於「關係」:改屬「人」,和 `cards_keepsake` 一起。清掉關係時它留著,定期的結清照樣看到它:卡號沒有卡就經錢包把扣的退回再刪(經濟的帳本也屬於「關係」,和它一起清掉時退的是 0,這一列一樣刪掉)。清掉人(會連關係一起清)時它才跟著走,那時人和錢包都沒了。
- **紀念卡上她寫的話**(§11.1「事後補寫」,2026-11-17 加):紀念卡照舊在打開卡片時只印事實發出去,不等模型。`cards` 模組另外有一個低優先的背景工作:啟動 3 分鐘後一次、之後每 30 分鐘一次,每次最多 3 張,找還沒有她的話的紀念卡(最舊的先),經 `CardFacesKey`(api 的寫法,同一套審核和「不寫別人的名字」)請她寫一句,告訴她這是紀念卡、卡上已經印了什麼;只取 line 放上卡(事實欄位、名字、編號都不動),卡的 `artifact_id` 清掉,api 記著的整張卡的圖(`/og/card`、`/me card` 附的那張)也丟掉(`CardFaces.rewritten`);她的立繪和字無關,不重算。預算照其他背景的模型工作(心智、晚上的反省):沒有 api 的寫法、沒有模型、或模型的每日預算不是 `ok`(degraded 或 exhausted)就不跑。寫不出來(模型失敗、被審核擋掉、她現在不說這個人)記一次(`face.line_tries`),最多試 3 次就不再試。卡上已經有話就不覆蓋;進度都在卡上,重跑、重啟都安全。

- 她有 `web_read`,可以打開一個網址讀文字(標題和正文)。它不執行網頁的程式、不能點、不能登入,所以靠程式畫出內容的網站(X、Instagram、多數影音網站)讀不到東西。
- 她看得到的圖只有訊息的附件,而且只從 Discord 的兩個網域下載(`[vision] allowed_hosts`)。
- 連結預覽(Discord 的 embed)只留標題、描述、網址(`EmbedSchema`),預覽圖在 `packages/discord/src/mapping.ts` 就丟掉了。`web_read` 也不回傳網頁上的圖。

可以做的:

1. 連結預覽的圖當成那則訊息的圖給她看。Discord 已經把它轉存在自己的代理網域,所以下載的對象仍然只有 Discord。
2. `web_read` 回傳網頁的主圖(`og:image`)和正文裡的圖的網址,加一個「看這張圖」的工具;下載走 `web` 模組已有的檢查(只連公開位址、大小上限、每人次數上限)。
3. 真的瀏覽(點、捲、執行網頁的程式):要一個無頭瀏覽器當工具,花費和風險都高一截,先不做,和「更省的搜尋方式」一起評估。

- 離線(不連任何模型,不花錢):`pnpm --filter @miyoria/eval test -- live-play`。檢查用的程式、題目、整個 suite 都跑在寫好答案的假模型、假評審和假受測對象上;`self` 受測對象收到 `world` 喚醒也在這裡測。harness 本身沒有錄好的模型,所以「離線」量的是評分器,不是模型。
- 對真的模型:`pnpm eval --live --config <miyoria.toml> --suite play --repeat 8 --max-usd 0.5`。只跑一部分:設 `EVAL_PLAY_ONLY`,例如 `EVAL_PLAY_ONLY=soup,fortune`(可用 `card`、`milestone`、`told`、`soup`、`soup-referee`、`soup-host`、`fortune`)。結果檔和趨勢照 `feel` 的:`data/eval/live/`,一行進 `history.jsonl`。

沒量到的:

- 檢查「在不在她的語氣」靠評審,評審和受測的是同一個模型;口氣的好壞最後還是要人看一次失敗的那幾筆。
- 檢查名字用的是一串編出來的名字,模型寫了清單以外的人名不會被抓到;真正的過濾是卡片自己的 `pass`,評測看的是在它之前模型有沒有守規矩。
- 完整的海龜湯流程(開局、計時、多輪問答、結束)沒有接真的 `Table` 和 `SoupGame`(要一個假的 Discord 和計時器),所以只量「一輪」。`writeCard` 和 `writeFortune` 在 `packages/api`,`tools/eval` 沒有它的依賴(加依賴要重新安裝),所以評測用路徑 import;要改成正式依賴時,在 `tools/eval/package.json` 加 `@miyoria/api` 再換掉 `play.ts` 開頭的兩行 import。

### 11.5 圖片訊息:做了什麼

**樣子**照 `apps/panel/DESIGN.md`,沒有另外的風格:上面一條 `.glass-dock` 的框(標記、「分類 / 頁面」、右邊放日期),下面整片 `.glass-sheet`,都貼齊邊,沒有浮起來的卡片。玻璃是 sharp 把背景圖那一塊做高斯模糊、調暗、加飽和(數值和面板的 CSS 相同),SVG 再蓋半透明的填色和細線;字有面板的陰影。內容用面板的零件:區塊標題 15、圖表區的標題 13 和 24 的數字、事實列(標籤在上、值在下,沒有格子)、細線分隔的列、`ColumnChart`、`BarList`、`SegmentBar`、`Meter` 和階梯、稀有度標籤、羈絆的環(和面板同一個 `BondRing`)。只有兩個強調色,類別色照固定順序。邏輯寬 540,輸出兩倍,1080 px 寬。
